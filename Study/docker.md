# 🌟 요약
- 가상머신과 도커: VM은 무거운 Guest OS까지 통째로 가상화하지만, 도커는 Host OS 커널을 공유하여 프로세스만 가볍고 빠르게 격리함
- 도커 이미지: 실행에 필요한 모든 환경을 압축해 둔 읽기 전용 설계도(파일)
- 도커 컨테이너: 이미지라는 설계도를 바탕으로 독립된 공간에서 실행 중인 실제 프로세스
- 도커 컴포즈: 여러 컨테이너의 설정을 파일 하나에 정의하여 한 번에 일괄 실행·관리하는 도구
- 도커 허브: 작성된 도커 이미지를 공유, 저장, 다운로드할 수 있는 중앙 레지스트리 (GitHub의 이미지 버전)
- 도커 엔진: 컨테이너를 생성, 실행, 관리하는 도커의 핵심 런타임 플랫폼
- 도커 명령어: 데몬에게 컨테이너 및 이미지 제어(생성·실행·삭제 등)를 요청하는 CLI 구문
- 도커 클라이언트: 사용자가 도커 명령어를 입력하면 이를 데몬에게 전달하는 전달자(CLI/GUI)
- 도커 데몬 (dockerd): 백그라운드에서 상주하며 클라이언트의 요청을 받아 실제 작업을 수행하는 Engine

## 📌 도커 핵심 개념
* **이미지** 
  * 애플리케이션 실행에 필요한 코드, 라이브러리, 환경 설정을 명시한 템플릿 (컨테이너 생성을 위한 설계도 → 없으면 컨테이너 생성·실행 불가)
* **컨테이너** 
  * 이미지를 실행한 상태. 독립된 공간에서 실제 프로세스로 동작하며 생성·수정·삭제가 자유로움
* **도커 허브** 
  * 작성된 이미지를 공유하고 다운로드할 수 있는 중앙 레지스트리 (GitHub 같은 이미지 저장소)

```text
[사용자 (Client)] ──(docker run)──> [Docker Daemon]
                                          │
                        ┌─────────────────┴─────────────────┐
                 (이미지 없음)                           (이미지 있음)
                        │                                   │
                        ▼                                   ▼
              [Docker Hub에서 pull] ───────────────> [컨테이너 생성 및 실행]
```

## 📌 도커 작동 원리 및 아키텍처

- **클라이언트-서버 구조:**
  - **Docker Client:** 사용자가 입력하는 CLI 명령어 (`docker run`, `docker build` 등)를 받음
  - **Docker Daemon (`dockerd`):** Background에서 실행되며, 클라이언트의 요청을 받아 이미지 생성, 컨테이너 실행 및 관리를 실제 담당

## 📌 가상머신과 차이점

> 도커는 무거운 Guest OS를 떼어내고, 내 컴퓨터(호스트) OS 커널을 공유해 VM의 성능 저하와 자원 낭비를 보완하며 등장

| 구분 | 가상머신 (VM) | 도커 컨테이너 (Container) |
| :--- | :--- | :--- |
| **구조** | Host OS ➔ Hypervisor ➔ Guest OS ➔ App | Host OS ➔ Docker Engine (Kernel 공유) ➔ App |
| **용량 & 속도** | OS 포함으로 무겁고 부팅이 느림 | 호스트 커널을 공유하여 가볍고 부팅이 빠름 |
| **자원 효율** | 자원을 미리 할당하여 낭비 발생 | 필요한 만큼 가변적으로 자원 사용 |

- **공통점:** 둘 다 애플리케이션을 독립된 환경(격리)에서 실행하기 위해 만든 기술
- **차이점:** "OS 전체를 가상화하느냐, 프로세스만 격리하느냐"의 차이
  - *비유:* 가상머신이 아파트 한 동(OS)을 새로 지어 들어가는 방식이라면, 도커는 하나의 아파트 안에서 방(프로세스)만 따로 격리해서 쓰는 방식

## 📌 도커 핵심 명령어

### 명령어 모음

| 구분 | 명령어 | 주요 역할 및 설명 |
| :--- | :--- | :--- |
| **컨테이너 실행 및 제어** | `docker run [옵션] [이미지]` | • 이미지를 기반으로 새 컨테이너 생성 및 실행<br>• `-d`: 백그라운드 실행<br>• `-p [호스트포트]:[컨테이너포트]`: 포트 포워딩<br>• `--name [이름]`: 컨테이너 이름 지정<br>• `-v [호스트경로]:[컨테이너경로]`: 볼륨(디렉토리) 바인딩<br>• `-e [환경변수]=[값]`: 환경변수 설정 |
| | `docker stop [컨테이너]` | • 실행 중인 컨테이너 정지 |
| | `docker start [컨테이너]` | • 정지된 컨테이너 재실행 |
| | `docker restart [컨테이너]` | • 컨테이너 재부팅 |
| **조회 및 상태 확인** | `docker ps` | • 현재 실행 중인 컨테이너 목록 조회 |
| | `docker ps -a` | • 정지된 컨테이너 포함 전체 목록 조회 |
| | `docker logs [옵션] [컨테이너]` | • 컨테이너 내부 로그 출력 (`-f` 옵션 추가 시 실시간 스트리밍) |
| | `docker exec -it [컨테이너] [명령어]` | • 실행 중인 컨테이너 내부에 접속/명령어 실행<br>(예: `docker exec -it my-mysql bash`) |
| **삭제 및 정리** | `docker rm [컨테이너]` | • 컨테이너 삭제 (정지 상태에서 가능, `-f` 사용 시 강제 삭제) |
| | `docker rmi [이미지]` | • 다운로드된 이미지 삭제 |
| **이미지 관리** | `docker pull [이미지]` | • 도커 허브에서 이미지 다운로드 |
| | `docker images` | • 로컬에 보유한 이미지 목록 조회 |

### 실행 예시 및 옵션 상세

```bash
docker run --name mysql-todo \                         # 컨테이너 이름 설정 & 실행
-e MYSQL_ROOT_PASSWORD=root_user_password_setting \    # 컨테이너 환경변수 설정
-e MYSQL_DATABASE=db_name_setting \
-e MYSQL_PASSWORD=user_password_setting \
-e MYSQL_USER=user_name_setting \ 
-p 3306:3306 \                                         # 포트 포워딩
-v mysql-todo-data:/var/lib/mysql \                    # 볼륨 바인딩 
-d mysql:8.0                                           # 백그라운드 실행
```

* **자동 이미지 다운로드→**  로컬에 `mysql:8.0` 이미지가 없으면, 도커 데몬이 자동으로 도커 허브에서 다운(pull)한 뒤 컨테이너 실행
* **포트 포워딩 (`-p`)→**  내 컴퓨터(호스트)의 NN 포트로 들어온 요청을 컨테이너 내부 MM 포트로 전달 설정
  * *효과:* 만약 내 컴퓨터(호스트)가 이미 MM 포트를 사용 중이면, `-p NN:MM`처럼 호스트 포트만 NN으로 바꿔서 충돌 없이 띄울 수 있음
* **볼륨 바인딩 (`-v`)→**  컨테이너 내부 디렉토리와 내 컴퓨터(또는 도커 전용 볼륨) 저장소를 서로 연결(마운트)
  * *필요성:* 컨테이너는 삭제되면 내부 데이터가 완전히 날아가는 휘발성 구조
  * *효과:* DB 데이터가 저장되는 컨테이너 안의 `/var/lib/mysql` 경로를 외부 저장소(`mysql-todo-data`)에 연결해 두면, 컨테이너를 삭제하고 다시 만들어도 DB 데이터가 안전하게 보존됨
* **백그라운드 실행 (`-d`)→**  컨테이너를 터미널과 분리해, 터미널 창을 닫아도 뒤에서 계속 컨테이너가 실행되도록 함

## 📌 도커 컴포즈 

* **1 컨테이너 = 1 프로세스 (원칙):** 
  * 애플리케이션이 MySQL, Redis 등 여러 프로세스를 모두 사용하더라도 각자 전용 컨테이너를 별도로 생성하여 실행함
* **분리하는 이유:**
  * **안정성:** 하나의 DB에 장애가 나거나 재부팅을 해도 다른 DB에 영향이 없음
  * **독립 관리:** 버전 업데이트, 리소스 제한, 설정 변경을 DB별로 개별 적용 가능
* **다중 컨테이너 관리:** 
  * `docker-compose`를 이용하면 여러 컨테이너를 파일 하나에 정의하고 명령어 한 번으로 일괄 실행·관리 가능

#### 작동 예시

**0️⃣ `docker-compose.yml` 파일 작성**

```yaml
version: '3.8'

services:
  # MySQL 컨테이너 설정
  mysql:
    image: mysql:8.0
    container_name: mysql-todo
    ports:
      - "3306:3306"
    environment:
      MYSQL_ROOT_PASSWORD: root_user_password
      MYSQL_DATABASE: mydatabase
      MYSQL_USER: myuser
      MYSQL_PASSWORD: user_password
    volumes:
      - mysql-data:/var/lib/mysql
    restart: always

  # Redis 컨테이너 설정
  redis:
    image: redis:alpine
    container_name: redis-todo
    ports:
      - "6379:6379"
    volumes:
      - redis-data:/data
    restart: always

# 영속성 유지를 위한 도커 볼륨 정의
volumes:
  mysql-data:
  redis-data:
```

**1️⃣ 실행**
- 일괄 실행: 각 컨테이너별 `docker run` 명령 필요 없이, docker-compose.yml 파일이 위치한 디렉터리에서 명령어 실행만으로 정의된 모든 컨테이너를 일괄 생성 및 실행함

```Bash
docker compose up -d
```

**2️⃣ 상태 확인**
```Bash
docker compose ps
```

**3️⃣ 종료 및 삭제**
```Bash
docker compose down
```
