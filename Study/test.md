# Spring Boot 계층별 테스트 핵심 요약

---

## 0. 테스트 코드의 필요성
* **수동 테스트의 한계:** 매번 앱을 다시 빌드하고 실행하여 API를 직접 호출해 보는 방식은 프로젝트 규모가 커질수록 테스트 시간이 기하급수적으로 늘어남.
* **개발 및 유지보수 생산성 향상:** 테스트 코드를 작성하는 시간이 추가되더라도, 자동화된 검증을 통해 전체 개발/수정 피드백 시간을 획기적으로 단축.
* **코드 수정 용이:** 코드 수정 시 기존 기능에 영향을 주었는지 빠르게 확인할 수 있어, 예상치 못한 영향을 즉시 감지 가능.

---

## 1. 계층별 테스트 핵심 요약

### 1) 컨트롤러 테스트 (`TodoControllerTests`)
* **목적:** 웹 계층 슬라이스 테스트 (HTTP 요청/응답, JSON 매핑, 상태 코드 검증)
* **핵심 도구:**
  * `@WebMvcTest`: 웹 관련 빈만 가볍게 로드
  * `MockMvc`: 가상 HTTP 요청 실행 (`perform`)
  * `@MockBean` / `given().willReturn()`: 하위 계층(서비스) 모킹 (Mockito)
  * `andExpect(status())`, `jsonPath()`: HTTP 응답 상태 및 JSON 값 검증

### 2) 서비스 테스트 (`TodoServiceTests`)
* **목적:** 순수 비즈니스 로직 및 도메인 데이터 검증 (HTTP/웹 요소 제외)
* **핵심 도구:**
  * `@BeforeEach`: 테스트 간 상태 오염을 막기 위한 전처리/초기화
  * `assertThat()`: 리턴된 객체/리스트의 필드값, 크기 등 검증 (AssertJ)

## 2. 순수 단위 테스트 vs 통합 테스트

| 구분 | 순수 단위 테스트 (Unit Test) | 통합 테스트 (Integration Test) |
| :--- | :--- | :--- |
| **스프링 로드** | **안 함** (스프링 컨텍스트 미기동) | **함** (`@SpringBootTest` 등으로 전체/부분 로드) |
| **의존성 처리** | `new`로 직접 생성하거나 `@Mock`으로 대체 | 실제 스프링 빈(Bean)을 주입받아 사용 |
| **실행 속도** | **매우 빠름** (밀리초 단위) | 상대적으로 느림 (컨텍스트 로딩 시간 소요) |
| **검증 범위** | 단일 클래스/메서드의 로직 격리 검증 | 여러 계층(DB, 네트워크, 스프링 설정 등) 간 연동 검증 |

> **핵심 구분 포인트**  
> **검증 목적:** 단위 테스트는 **"단일 부품/로직의 완벽함"**을, 통합 테스트는 **"부품 간 실제 결합 시 정상 동작"**을 검증함.

---

## 3. Mockito vs AssertJ (assertThat) 역할 및 차이

### 1) Mockito (의존성 가짜화 / Stubbing)
* **역할:** 테스트 대상이 의존하는 하위 객체를 가짜(Mock)로 만들고 행동을 정의 (`given().willReturn()`)
* **쓰임:** 컨트롤러 테스트 시 진짜 서비스를 실행하지 않고 가짜 응답을 반환하도록 설정하거나, 서비스 테스트 시 DB/외부 API 조회를 가짜 데이터로 대체할 때 사용

### 2) AssertJ `assertThat` (결과 검증 / Assertion)
* **역할:** 메서드 실행 후 반환된 실제 결과값(자바 객체)이 예상과 일치하는지 검증
* **쓰임:** `assertThat(result).isEqualTo(expected)`, `hasSize(2)` 처럼 자바 객체의 필드값, 크기, Null 여부 등을 최종 단언(Assert)할 때 사용

### 3) 차이점 한 줄 요약
* **Mockito**는 테스트 실행 전 **"환경 세팅(가짜 의존성 준비)"**을 담당하고, **AssertJ**는 테스트 실행 후 **"결과 검증"**을 담당함.
